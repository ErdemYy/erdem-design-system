# Tools: Automation (automatic intelligence refresh, context routing and change impact)

Implements one rule of `ai/AUTOMATION_PROTOCOL.md`: when the agent may refresh derived project intelligence without asking. There is no second indexer or graph engine here. The work is done by the existing `runIndex` and `runGraph` (`lib/pipeline.mjs`); this directory only decides whether to run them and checks the result.

```
automation/refresh-decision.mjs   shouldAutoRefresh(input): the one pure decision function
automation/refresh.mjs            autoRefresh(root, task): gathers facts, decides, runs the engine (can read git, can write through the engine)
automation/context-router.mjs     routeContext(task, intelligence, project): the context router (pure, read-only)
automation/context-sources.mjs    its tables: levels, questions, class ceilings, design concerns, platforms, graph questions
automation/change-impact.mjs      analyzeChangeImpact(changeSet, intelligence, project): bounded change impact (pure, read-only)
automation/path-safety.mjs        the one path filter: cleanPath, isSecretPath, guardPaths
automation/records.mjs            pure helpers shared by both: classifyState, actionRecord
../lib/artifact-paths.mjs         the one set of derived-artifact names (slug), used by the generator, the router and refresh
```

Command: `project-intel refresh [root] [--config <file>] --relies-on <list> [--scope <paths>] [--class <c>] [--risk <r>] [--event <e>] [--search-insufficient] [--declined <reasons>] [--after-failure] [--check] [--json]`. Library: `shouldAutoRefresh`, `autoRefresh`, `classifyState`, `trackedUnder` (exported from `api.mjs`). Adapters pass the command through (`intel refresh ...`); they hold no refresh logic.

## Decision

`shouldAutoRefresh` returns `{decision, reason, level, affectedArtifacts, command, detail}`. Decisions: `AUTO_REFRESH` (A1, run it), `NO_REFRESH`, `PROPOSE_REFRESH` (A2, ask first), `BLOCKED` (A0, manual only).

**AUTO_REFRESH** only when all hold: the output directory exists; the session state is `stale` or `partial` (`adapters/GENERIC.md` section 3); the task relies on a stale or missing artifact (what it relies on is stated by the caller, `--relies-on`; the task class is recorded but is never proof); no file the run could write is tracked by version control.

| Situation | Decision (reason) |
|---|---|
| a manual operation was asked for: rehash, forced rebuild, profile change, discarded cache, configuration change, cleanup | BLOCKED, A0 (`manual-operation`) |
| event SESSION_START | NO_REFRESH (`session-start`) |
| status unavailable (cannot run, times out, unreadable, invalid configuration) | NO_REFRESH (`status-unavailable`); never retried |
| a refresh already failed in this session (`--after-failure`) | NO_REFRESH (`refresh-failed-earlier`) |
| current | NO_REFRESH (`state-current`) |
| unverifiable | NO_REFRESH (`unverifiable-not-refreshable`): a refresh cannot make a source fingerprintable |
| missing | NO_REFRESH (`missing-targeted-inspection`), or PROPOSE_REFRESH (`first-index`, A2) when the task relies on intelligence, targeted search was not enough (`--search-insufficient`), and the class is MEDIUM or larger or the risk HIGH or CRITICAL |
| every proposal reason that applies was declined (`--declined <reasons>`) | NO_REFRESH (`declined-earlier`, record result `declined`, `detail.suppressed` lists the reasons) |
| stale or partial, nothing relied on | NO_REFRESH (`no-reliance`, `artifacts-not-relied-on`) |
| relied on, version-control status unknown (not a git work tree, git missing) | PROPOSE_REFRESH (`vcs-unknown`) |
| relied on, a file the run could write is tracked (paths compared case-insensitively on Windows and macOS, case-sensitively elsewhere) | PROPOSE_REFRESH (`derived-files-tracked`) |
| relied on, the effective configuration differs from the one that produced the artifacts (stale because the configuration changed), for example `--config` was not given | PROPOSE_REFRESH (`configuration-changed`) |
| index-level run and the declared profile is unknown, or the configuration names a different profile | PROPOSE_REFRESH (`profile-unknown`, `profile-differs-from-config`) |
| all conditions hold | AUTO_REFRESH (`relied-on-stale`) |

## Declining

A decline is about one proposal reason (`first-index`, `profile-unknown`, `profile-differs-from-config`, `configuration-changed`, `vcs-unknown`, `derived-files-tracked`). The caller remembers the reasons the user declined in this session and passes them as `--declined a,b`; the tool stores nothing, so a new session starts with an empty list and may propose again. A declined reason is not proposed again; any other applicable reason still is (the proposal is the first applicable reason that was not declined). When every applicable reason was declined the answer is `NO_REFRESH`: a declined blocker never becomes an automatic refresh. A BLOCKED refusal (A0, or a missing output directory) is never suppressed. A bare `--declined` or an unknown reason is a usage error.

## What a refresh does

- **Configuration:** `--config <file>` is used for every engine call (`loadConfig`, `status`, `index`, `graph`, the check afterwards), so a refresh never runs under a different effective configuration than the one that produced the intelligence. A missing file is a usage error.

- **Command choice:** only graph artifacts relied on → `runGraph` (writes `graph/` and `state/parse-cache.json`); anything else → `runIndex`, pinned to the profile declared in `index.json`. Both are incremental: unchanged artifacts keep their bytes and unchanged files reuse the parse cache.
- **Never deletes:** `runIndex` is called with `prune: false`, so obsolete derived files are left for a user-run `index` to clean up. Every other `index` invocation keeps its cleanup.
- **Never:** `--rehash`, a profile change, a first index, a configuration change, a commit, staging or `.gitignore` changes. Tracked status is only read (`git ls-files`, no shell).
- **Written paths** are checked after the run against the permitted set (`mayWrite`). The relied-on artifacts are checked again with `status`; if any is still stale or missing the result is `failed`.
- **Tracked-file check** covers everything the chosen command may write under the output directory; `TASK_STATE.md`, `HANDOFF.md` and `DECISIONS.md` are never in that set.

## Failure and records

A failure (engine error, written outside the set, artifact still stale) gives `result: failed`, exit 1 and no retry; the caller continues from source and does not treat intelligence as current. The action record is the Phase 5A format (`v, event, action, reason, scope, level, result, detail, at`), printed and not stored. It holds counts and enumerated words only, never file contents or absolute paths. Exit codes: 0 no refresh needed or refresh succeeded; 1 a proposal, a refusal or a failed refresh needs attention; 2 usage error.

## Arguments

Nothing that changes meaning is silently ignored. `--event`, `--class` and `--risk` must be canonical values; `--relies-on` must name known things; `--scope` paths must be project-relative and stay inside the project; options of other commands (`--view`, `--depth`, `--target`, `--max-nodes`, `--include-*`, `--stdout`) and extra positional arguments are usage errors (exit 2). `--rehash` and `--profile` are recognised and refused (BLOCKED, A0). The older commands (`index`, `graph`, `status`, `impact`) keep their behavior, including options they do not use.

## Context routing

`automation/context-router.mjs` (tables in `automation/context-sources.mjs`) implements the "Context automation" section of the contract: the minimum sufficient context, one level at a time. It is pure and read-only (no file access, no process, no network); the agent carries out the reads it names.

Command: `project-intel route [root] --class <c> --risk <r> --types <list> --targets <paths> [--subsystem <dir>] [--kind design|implementation|mixed] [--platform <p>] [--concerns <list>] [--signals <list>] [--queries <list>] [--intent change|read-only] [--event <e>] [--state <s> [--artifacts k=v,..]] [--reached <n>] [--answers 1=read,4=open,..] [--loaded path=unchanged|changed|unknown,..] [--escalation-reason <r>] [--between from,to] [--searched] [--json]`. Library: `routeContext(task, intelligence, project)`, `evaluateSufficiency(answers, ctx)`, `impactNeed`, `validationNeeds`, `intelligenceFromStatus`. Without `--state` it runs one read-only status check; with it, it reuses the state the caller already holds.

- **Facts, not text:** the caller states the class, risk, types and signals (`publicSurface`, `crossSubsystem`, `layerBoundary`, `dependencyUncertain`, ...). Routing never classifies from free text. The class is raised by signals and by the type floors of `ai/TASK_ROUTING.md`, never lowered.
- **Levels:** the six canonical levels, none added. `minimumLevel` is the lowest level that can answer the five questions for this kind of task; `ceiling` is the class default raised by risk and signals. The answer to the five questions, not the class, decides when to stop: a MEDIUM task may stop at Level 2, an ARCHITECTURAL one at Level 4. Level 5 is the minimum only for a layer boundary, unresolved architecture, or CRITICAL security or migration work.
- **One level at a time:** each call returns the plan for the next level. Only Level 1 (class and scope known from the request) and, for TRIVIAL and SMALL, Level 2 (target known) may be skipped, each with a stated reason in `skipped`.
- **Sufficiency:** `evaluateSufficiency` answers sufficient or insufficient, names the open question, and says `deepen`, `search`, `ask` or `refuse`. Assumptions are not evidence; for HIGH and CRITICAL risk, "what depends on it" needs search or graph evidence. Past the ceiling an open dependency or validation question may go one step on its own account; any other step needs a reason from the list (`ESCALATION_REASONS`); "might be useful" is refused.
- **Intelligence:** current is trusted; stale is a hint and impact falls back to source search; unverifiable is provisional and never used for impact; partial uses the artifacts that are current and names the missing areas; missing and unavailable use the repository. The plan only names the reliance tokens to pass to `project-intel refresh`; routing never refreshes, indexes or retries.
- **Graph questions** follow the capability matrix (`tools/analyze/README.md`): command form (`impact <file> --json`, read-only) where one exists, `via: "library"` with the function name for library-only questions (shortest path), source search otherwise. A command form that writes derived files (`graph --view`) is never planned.
- **Canonical documents:** protocol documents by need (`ai/SAFE_MODIFICATION.md` for sensitive changes, `ai/CHANGE_IMPACT.md` at Level 4, `ai/VALIDATION_PROTOCOL.md` for V2 and deeper, the safety, validation and secrets protocols for security work); design concerns and the target platform's files for design work only, at most six concerns (more is an error); implementation tasks load none.
- **No repeats:** files the caller reports as held and unchanged are listed under `skip`; changed or unknown ones are flagged `recheck`. Secret-pattern targets are `withheld` and never planned.
- **Record:** the plan carries a Phase 5A action record (`context-route`), printed and not stored.
- **Minimum and ceiling come from one list of drivers** (`levelDrivers`): class, the refactor/dependency/migration/security type floors, public surface, HIGH or CRITICAL risk, build or runtime configuration, dependency uncertainty, and the Level 5 conditions. The minimum is the deepest driver, the ceiling is the class default raised by every driver, so `minimumLevel <= ceiling` always holds and each level above the class default is explained by its own reason in `reasons` (`task-type-floor`, `dependency-uncertainty`, `configuration-or-api-impact`, `public-surface`, `required-by-risk`, `architectural-dependency`, `security-boundary`, `migration`); `class-default` when nothing raises it. Record reason codes are the Phase 5A ones (`recordCode`).
- **Target cap:** a plan names at most 12 targets (`MAX_TARGETS`). No canonical document fixes a number (`ai/CONTEXT_PROTOCOL.md` defines no token figure); the cap is an operational bound so that one level's plan stays a short list. The caller's order is kept and taken as priority; secret paths are withheld first and use no slot. Nothing is dropped silently: `targets` reports `{targetLimit, planned, truncated, remainingTargets, remainingBySubsystem, batchingRequired}` and a note says to route the rest in batches by subsystem.
- **One path filter** (`path-safety.mjs`) for every path a plan names: targets, subsystem, architecture documents, canonical documents, queries. It is the scanner's secret-pattern list (`lib/secret-patterns.mjs`) applied to the path and to each directory above it; withheld paths are listed in `withheld` and never planned. Filtering comes before any bound.
- **Paths:** project-relative, forward slashes. Brackets and braces are literal (`app/[id]/page.tsx`, `app/[[lang]]/page.tsx`, `app/[...slug]/page.tsx`, `src/routes/{id}.tsx`). A path is refused as a glob when it contains `*` or `?`, a bracket class with a negation or a single-character range (`[!x]`, `[^x]`, `[a-z]`), a brace group with alternatives or a range (`{a,b}`, `{1..3}`), or unbalanced brackets or braces. Absolute, UNC, drive-letter and `..` paths are refused.
- **Artifact names:** directory indexes and summaries are named by `lib/artifact-paths.mjs` (`slugPath`: every character outside `A-Za-z0-9._/-` becomes `_`, so `src/my dir` is `src/my_dir` and `src/Ünlü` is `src/_nl_`). The generator, the router and the refresh scope matching all use it; existing artifact names are unchanged.
- **Shortest path** needs two endpoints, `--between from,to` (`pathBetween`), never taken from the targets. With fewer or unusable ones the plan lists the requirement under `unresolvedRequirements` and plans no query. It is library-only (`shortestPath(from, to)`); with an untrusted graph it becomes a two-endpoint source search.
- **`configImpact`, `apiImpact`, `dataImpact`, `platformImpact`, `designSystemImpact` are query hints.** `ai/CHANGE_IMPACT.md` lists them as dimensions to find during impact analysis (Level 4); depth is set by class, risk, public surface and dependency uncertainty, not by them. They add a source search each at Level 4 when impact is needed and change nothing else.
- **The refresh hint** (`intelligence.refresh`) names only what the plan uses as a hint or could not trust: the stale index at Level 0, the directory index at Level 2, the graph at Level 4, and only where a refresh could help (stale or missing, never current or unverifiable). Level 3 reads source and names none.
- **Structurally read-only:** the router's whole import closure is `context-router`, `context-sources`, `path-safety`, `records`, `refresh-decision`, `lib/artifact-paths`, `lib/secret-patterns` and `lib/glob`: no file, process or network module, and not `refresh.mjs`.

## Change impact

`automation/change-impact.mjs` implements "what should be re-evaluated after a change" (`ai/CHANGE_IMPACT.md`, `ai/AUTOMATION_PROTOCOL.md` → Change impact). It orchestrates what exists and builds none of it again: the graph and its queries are `analyze/query.mjs` (supplied by the command as a query object), risk and public surface are the engine's own per-node values, class, risk floors and validation depth come from the context router, artifact names from `lib/artifact-paths.mjs`, the refresh decision from `automation/refresh.mjs`. It is pure and read-only (its import closure has no file, process or network module and does not include refresh), runs no test, writes nothing and refreshes nothing.

Command: `project-intel change-impact [root] --modified <list> --created <list> --deleted <list> --renamed old=new,.. [--phase planned|completed] [--class <c>] [--risk <r>] [--types <list>] [--signals <list>] [--state <s> [--artifacts k=v,..]] [--fresh-graph] [--reached <n>] [--loaded paths] [--config <file>] [--json]`. Library: `analyzeChangeImpact(changeSet, intelligence, project)`, `normalizeChangeSet`, `predictIntelligenceImpact`, `IMPACT_BOUNDS`.

- **Change set:** explicit (`{files: [{path, status, from?}], phase, taskClass, risk, taskTypes, signals}`; statuses created, modified, deleted, renamed). Nothing is scanned for. A rename needs its old path; it is never inferred (no git is consulted). Secret-pattern paths are withheld and never analyzed.
- **The graph is used only when it can be trusted for this change:** a graph artifact whose state is current, or a graph built now from the current sources (`--fresh-graph`, the same in-memory build the `impact` command does). A stale, missing, unverifiable or unavailable graph is never presented as current: the report says `graph.used: false`, lists bounded source searches (`inspection`), has `confidence: low`, notes that the risk rises one level if targeted search cannot determine the impact, and the command asks the existing refresh decision what is allowed (`intelligenceImpact.refreshDecision`, decide only). After an edit the artifact is stale by definition, so the usual order is: refresh (Phase 5B), then analyze, or analyze before the change with `--phase planned`.
- **Direct impact:** dependents, dependencies, directly related tests and changed public surfaces, from `getImpact`. **Transitive impact:** dependents up to 3 levels, each once at its nearest distance (cycles terminate and are reported, bounded). Files of the change set are not listed as their own dependents.
- **Tests** are separated into direct tests (they depend on a changed file) and consumer tests (they depend on something that does); consumer tests are recommended only where justified (a public surface changed or depends on the change, risk MEDIUM or higher, class MEDIUM or larger). Nothing is run and no command is chosen.
- **Public surface:** a changed surface sets the canonical floors through the router (class and risk at least MEDIUM); a surface that merely depends on the change is reported, widens the test recommendation and asks for context, but does not reclassify the task.
- **The five dimensions** (configuration, api, data, platform, designSystem; no others) come from the caller's signals and, where the engine has the fact, from evidence: configuration from a config-category file or a global-config surface, api from entry-point surface reasons (`package-entry`, `configured-entry`, `framework-route`). Each reports `source`: signal, evidence, both or none.
- **Risk:** the stated risk and the engine's risk for the changed files, then the router's floors. A dependent's risk is reported as advisory (`propagation`) and not applied, because the canonical rules do not raise a change's risk by it. **Validation depth** is the router's (V0 to V4, raised by risk); the report adds the recommended tests.
- **Intelligence staleness** uses the engine's artifact kinds (graph, index, fileIndex, directoryIndex, summary) and its own staleness rules (the machine index lists every file; the graph and the navigation and file indexes follow source, test, config and generated files; directory indexes and summaries follow their member files); a test calibrates the prediction against a real status run. With the status artifact list it also names the affected artifacts, by the generated (slug) names.
- **Context to reopen** goes through the canonical router: the report calls `routeContext` with the facts it discovered and returns that plan, with reasons (`new-dependents`, `public-surface`, `dimension:*`, `risk-raised`, `tests-expanded`, `files-not-in-graph`, `graph-untrusted`, `all-withheld`). There is no routing logic in the module.
- **Deleted and renamed files:** dependents come from a graph that still contains the file (planned changes, or a graph from before the change); otherwise (and for a rename already applied, see Renames) they are `null` (unknown) with a search instead. The dependents of a deleted file will have unresolved imports; the dependents of a renamed file's old path are the files whose import paths need updating.
- **Unknown is not none** (one convention, no state vocabulary of its own): `null` = unknown (not evaluated, because there was no graph evidence), `[]` = known empty, `false`/`true` = known. When the graph is not used (stale, missing, unverifiable, unavailable, or every path withheld) every graph-derived field is `null`: dependents, dependencies, tests, public surface, cycles, subsystems, the per-file facts and the dimensions' evidence. A caller's signal stays known (`present: true, source: signal`); the dimensions that only have signals report `source: none` when nothing was signalled. `evidence.graph` says `known` or `unknown`.
- **Completeness:** `COMPLETE` (every list whole), `BOUNDED_COMPLETE` (the evidence was consulted but a stated bound cut a list, or the depth limit applies) and `PARTIAL` (some or all of the evidence could not be consulted). Confidence is `high` only for COMPLETE, `medium` for BOUNDED_COMPLETE or a file the graph does not know, `low` when the graph was not used. **A changed file whose language has no dependency analysis** (Python, Go, Rust, Java, CSS, shell: the engine records only metadata for them) makes the report `PARTIAL`: it is listed in `unanalyzed`, a limitation says that the files and tests that import it are unknown ("not none"), and when no changed file could be analyzed the dependents, transitive dependents, dependencies and affected tests are `null` (unknown), never an empty list. In a mixed change, what the analyzed files prove is kept and the rest is flagged.
- **Unclassified:** an omitted or null class goes to the router as unclassified (its own minimum, validation V1, raised by risk like any class), never as TRIVIAL (V0); a stated TRIVIAL stays V0. When every requested path was withheld the class is not lowered to V0 either, and the report says `evidence.allWithheld`, `evaluated: false`, reason `all-withheld`.
- **Renames:** the old path's dependents when the graph has it (`dependentsSource: old-path`); when the rename is already applied and only the new path is in the graph, the new path's dependents (`new-path`, a fact about the new path, not the old one); when neither is, `dependents: null`, a bounded search for the old path and the reason `files-not-in-graph`. Conflicting statuses are rejected: a path (or the old path a rename vacates, compared the way the file system compares) belongs to one change only, so modified-and-renamed-away, swaps, chains, two renames from or to one path and case-fold twins (on a case-insensitive system) are errors.
- **Subsystem:** the cross-subsystem fact is the engine's: the graph's node subsystem, or `subsystemOf` with the project's configured `subsystemRoots` (the command passes them). Two directories under one subsystem are not cross-subsystem, and nothing is guessed without the engine's roots.
- **Bounds** (no canonical number exists; operational, never silent): 20 changed files, 3 levels, 30 direct dependents, 40 transitive dependents, 30 direct dependencies, 30 dependents per deleted or renamed file, 20 tests, 20 affected public surfaces, 20 affected cycle members, 5 cycle groups, 8 members per group, 12 inspection searches, 6 dependents proposed for reopening. Order is deterministic: nearer first, public surface first, higher risk first, then path. Every list a bound can cut reports `{limit, total, returned, omitted, truncated}` under `bounded` (`null` total and truncated when unknown); a limitation says how many were left out, `bounded.truncatedLists` names them and `batching.required` is set when evidence was cut. `reopenDependents` is `informational` (all its items are in `directImpact.dependents`): reported, but it does not by itself force batching. The inspection says which files it searched and which it did not (`bounded.inspection.filesInspected`, `filesNotInspected`); a file is covered by both of its searches or not at all. The rest is grouped by subsystem (`remainingBySubsystem`). It never returns the whole graph.
- **Secrets:** a secret-pattern path is withheld from the change set and, whatever puts one into a list (dependents, dependencies, cycles, deleted or renamed dependents), the finished report is filtered once more with the same shared rule; the `withheld` list names paths only.
- **Fresh graph:** with `--fresh-graph` the router is told the graph is current for this change, so the reopen plan has no stale-graph reason; with a stale or missing graph it has (`graph-untrusted`).
- **Record:** a Phase 5A action record (`impact-analysis`, event `IMPACT_REQUIRED`), printed and not stored; counts only.

## Validation

Planning and execution are separate. A plan is made without running anything; execution runs only what the plan says.

```
automation/validation-classify.mjs   classifyText, classifyArgv, summarizeScript, pathTargeting: the level (A1, A2, A3) of a command, from verified read-only forms (pure)
automation/validation-discovery.mjs  discoverCommands, rediscoverCommand: the project's own manifests, read, never executed; a SHA-256 of what a command depends on
automation/validation-plan.mjs       planValidation({task, impact, routing, project}): the one canonical plan (pure, executes nothing)
automation/validation-runner.mjs     runValidationPlan(plan, root, opts): executes the A1 part of a plan; applyValidationToTaskState; supervisedSpawn
automation/validation-state.mjs      updateTaskState, handoffDecision, validationRecord, lastValidationLines (pure text)
automation/validation-supervisor.mjs  the process supervisor the runner starts: time and output limits, whole-process-tree termination on a timeout
```

Command: `project-intel validate [root] --modified <list> --created <list> --deleted <list> --renamed old=new [--class <c>] [--risk <r>] [--types <list>] [--signals <list>] [--fresh-graph] [--run] [--confirm <planId> [--confirm-reasons <list>]] [--declined <reasons>] [--opt-in commandId|scriptDigest|type|reason|scope] [--update-state --owner <name> [--task-state <path>] [--goal <text>]] [--task-status in-progress|blocked|done] [--session-ending] [--json]`. Without `--run` it only plans (exit 0, nothing written). It uses the Phase 5D impact report for the change set and the Phase 5C router through it (class, risk and validation floors), and builds neither again.

- **Depth** is the router's (`validationNeeds`: V0 to V4; HIGH uses the next class's validation, CRITICAL V4, unclassified V1). Impact and routing can only raise it, never lower it. No level is added.
- **Actions** are the canonical taxonomy: `syntax`, `unit-test`, `integration-test`, `type-check`, `lint`, `build`, `static-analysis`, `security-check`, `targeted-check`, and only those the project provides. V0: the narrowest sanity check of the changed files (the language's own parse-only mode; no project command is guessed). V1: lint and type check where declared, plus the narrowest targeted test (affected tests, when the project's test command can take paths). V2: the project's tests (targeted when possible, otherwise its declared script) plus the relevant checks. V3: tests, type check, lint and the build when the change can affect it (configuration, dependency or build task type, public exports, or impact unknown). V4: all of that plus integration, static-analysis and security checks the project defines. Narrowest first; migration and deployment checks are never automatic.
- **Commands come from the project.** `package.json` scripts by validation name (through the declared package manager, `pre` and `post` hooks and nested `npm run x` included in the classification); a tool the project names in `pyproject.toml`, `Cargo.toml` or `pom.xml` without declaring a command is only a proposal (`inferred-from-config`); Makefile, tox, gradle and the like are reported as present and not parsed. When no command exists the check is `unresolved` ("not run, no command defined"), never invented.
- **Levels.** A1: a known checker used in a form that is PROVEN read-only by a per-tool table of allowed flags and arguments (see Verified forms) (eslint, `tsc --noEmit`, `node --check`, `node --test`, `pytest`, `black --check`, `vitest run`, ...): whole-tool allowances do not exist. A2: unclear, `npx` and other package runners, audit, docker, expensive suites, formatters that write (`black .`, `isort .`, `ruff format .`, `rubocop -a`, `prettier --write`), `tsc` that may emit, servers and watchers (`vite`, `next dev`, `webpack serve`, `vitest` without `run`), a project script run by an interpreter (`node scripts/x.js`, reason `project-script`), environment expansion (`$VAR`, reason `env-expansion`), shell constructs, inferred commands; and V3 and V4 as a set (one proposal, one yes for that plan). A3, prohibited and never planned as runnable: install (including `python setup.py install`, `deno install`), publish, deploy, migration, version-control history, destructive commands, downloads, secret reads (a secret-named variable reaching a command included), privilege. A proposal states action, scope, reason, effect, a bounded redacted summary of the script and its hooks, and the alternative; a decline (`--declined <reason>`) is specific to its reason (`network-possible`, `external-tool`, `expensive`, `mutating`, `shell-construct`, `env-expansion`, `env-assignment`, `long-running`, `inferred-from-config`, `project-script`, `unclear-command`, `validation-set`).
- **Opt-in** (`--opt-in commandId|scriptDigest|type|reason+reason|scope`, library `{commandId, scriptDigest, type, reason, scope}`): lowers ONE named A2 action to A1 (rule 3: "a named action and scope"). The command id and the digest of its definition must match (a changed script, or an edit anywhere in its manifest's scripts table, is another action and the old opt-in is stale), the type must match, the reason set must EQUAL the action's reasons (an extra reason is a broader permission, a missing one does not cover it) and the scope must be exactly the action's canonical scope id (`project`, or `path:<dir>` of its manifest; broader and narrower are refused). The proposal prints the exact `optIn` that would name each action. `shell-construct` and `env-expansion` can never be lowered and an A3 never is. The V3/V4 set is authorized by its own exact identity, `validation-set|setId|depth|risk|project` (the set proposal prints it): `setId` is a SHA-256 over the depth, the risk, the scope and every action (command id, definition digest, type, scope, planned reasons, planned files), so another plan, depth, risk, scope, script or action set is another set and the old authorization does not apply; it lowers only verified-safe (A1) actions, never an A3, is checked again at run time (a plan lowered by it is refused without it) and is never stored. The runner needs the same list again at run time, otherwise a lowered action is refused. Nothing is stored. Provenance: `--opt-in` and `--confirm` are caller flags; this tool cannot verify that a user or a project rule gave them, the adapter must (the result says so when an action ran on one).
- **Identity.** `planId` is a SHA-256 over the depth, every action (id, type, level, argv, files, scope, classification, hooks and a digest of the whole scripts table of its manifest) and the proposals, prohibited and unresolved entries that cover them. A plan holds no script text, only the digest and a bounded, redacted summary. Right before an action runs its command is read again from the project: a script, hook, nested script or manifest that changed since planning is refused (`command-changed-since-planning`, `command-no-longer-defined`), the level is derived again from what is there now, and a level stricter than the planned one is refused (`runtime-classification-stricter`) unless the exact opt-in covers it; A3 is never run. A confirmation names a `planId`, so an old yes cannot authorize a changed command.
- **Execution** (`--run`): an argument vector with `shell: false`, from the project directory, with a time limit, an output limit and no stdin, under a supervisor that on a timeout terminates the whole process tree (Windows: `taskkill /T /F`; elsewhere the process group) and verifies it. Only `treeTerminated === true` is a clean timeout (UNKNOWN `timed-out`); false, undefined, a supervisor that fails and the supervisor's own outer timeout are UNKNOWN `timed-out-orphan-risk` / `supervisor-failed-orphan-risk` with a limitation, and an output overflow is held to the same rule. Windows `.cmd` and `.bat` shims are refused (`npm` runs as `node npm-cli.js`). **npm is pinned, not trusted**: the plan carries an `execution` record (`scriptShell: platform-default`, `ignoreScripts: false`, `prependNodePath: warn-only`, a digest of the resolved shell, never its path) that is part of the plan id; the runner passes `--script-shell=<cmd.exe of the system directory, or /bin/sh>`, `--ignore-scripts=false` and `--scripts-prepend-node-path=warn-only` on the command line (the highest-precedence source: it beats every `.npmrc` and every `npm_config_*` variable, none of which is read), removes every `npm_config_*` variable from the child environment, rebuilds the execution record right before running and refuses a mismatch (`command-changed-since-planning`, `execution-environment-changed`, `execution-environment-unavailable`); yarn, pnpm and bun cannot be pinned, so their actions are not run (`execution-environment-unpinned`). **What npm execution binds**: the script shell is pinned and bound (command line, part of the plan id); whether lifecycle scripts run and where the node path goes are pinned and bound likewise; `npm_config_*` variables are removed from the child environment. Not pinned: workspace selection and any other npm setting a `.npmrc` or the environment may supply. Not bound: a user-level `.npmrc`, a global `.npmrc`, `NODE_OPTIONS` and the rest of the inherited environment; npm itself may still read a `.npmrc`, which is why the pins are on the command line. The plan states this in `executionNotes` (standing facts, they do not lower confidence). `verify: false` exists only with an injected process layer (tests); a real process is never started without re-reading the command. **The arguments after the command are exactly the plan's own files**: the plan keeps the manifest command (`baseArgv`) apart from the planned files, the runner derives the arguments from those files again (`appendedArgsFor`) and refuses anything else (`appended-arguments-not-planned`), and refuses a planned file that is absolute, leaves the project, is empty or matches a secret pattern (`appended-argument-unsafe`). An A2 action runs only with `--confirm <planId>` for that plan; the first failure stops the rest (`stopped-after-failure`); nothing is retried, installed or changed to make a check pass. A reused result (`reused`) states that nothing was executed (`executed: []`) and is honoured only while the plan still matches its id and every command still has its planned digest. npm itself runs a script body through the platform shell, which is why the script text is classified; a project `.npmrc` is a secret pattern, is never read, only its existence is bound; the plan says npm itself may still read it for settings that are not pinned.
- **Results:** `PASS`, `FAIL`, `NOT_RUN`, `DECLINED`, `BLOCKED`, `UNKNOWN`; the overall status is the most serious one (FAIL, BLOCKED, DECLINED, UNKNOWN, NOT_RUN, PASS) and PASS needs every planned action to have passed with nothing unresolved or prohibited. Not run, declined and unknown are never a pass. Evidence is counts, durations and, for a failure, a short redacted excerpt with no absolute path; command output never enters state or a record.
- **TASK_STATE.md** (the one state record): the outcome is written into ONE owned block (`<!-- erdem:validation:begin ... -->` to `<!-- erdem:validation:end -->`) inside `## Last validation`: the result line (plan and content keys), one line per action, `- open:` and `- problem:` lines. Only the block and the `updatedAt` value change; every other byte (user lines that happen to begin with "validation", indented items, numbering, other sections, LF or CRLF) is preserved. Written when validation completes, by the current owner only, created only when a canonical trigger holds, identical updates and reused results skipped; a LARGE or ARCHITECTURAL plan is recorded once, in the same block. **State and handoff are one decision** (`decideValidationStateAndHandoff`, pure): a handoff is required only when the session is ending (or cannot continue) with the task unfinished and validation not passed, when ownership is transferred, when validation is BLOCKED (a boundary only a person can resolve) on unfinished work, or when an A2 cannot be asked about and work remains; a DECLINED or UNKNOWN validation in a session that continues is recorded in TASK_STATE.md, which is sufficient. A required handoff always makes the state required first (creation trigger "a handoff is about to be written"; the order is TASK_STATE.md, then one new HANDOFF.md, never a duplicate), so the two can never disagree; a task cannot be called done while its required validation has not passed (`completion.allowed`). **Record:** the Phase 5A action record (`VALIDATION_REQUIRED` when planned, `VALIDATION_COMPLETED` when finished), counts and words only; the canonical result words have no "unknown", so UNKNOWN is `failed` there and stays UNKNOWN in `detail.status`.
- **Unknown is not none:** an unknown affected-test list, public surface or configuration impact is never read as "no tests" or "no build impact"; the plan says so, widens to the declared script or the build, lowers its confidence and, for MEDIUM and larger or HIGH risk, asks the router for context (`contextNeeds`). **Impact completeness is carried in:** the class is the highest of the task, the router and the impact report (never lowered); every requested path withheld is unevaluated (`required: true`, `evaluated: false`, unresolved `all-paths-withheld`, UNKNOWN), never "not required"; withheld paths among visible ones and `remainingChangedFiles` are stated, and changed files impact did not reach make the result UNKNOWN (`coverage`), never a clean PASS. A targeted run is called `narrow` only for runners known to replace what the script runs; jest, mocha and a script that already names paths are not, and a path a runner would read as a pattern (`[id]`) is not targeted.
- **Impact limitations are carried**: the impact report's limitations (at most 20, each at most 300 characters, hidden paths replaced, the rest counted) are copied into `plan.impact.limitations` and `plan.limitations` (prefixed `impact:`), with `completeness`, `confidence`, `truncatedLists`, `remainingChangedFiles`, `withheld`, `allWithheld` and `batchingRequired`. An impact that could not be established (graph unused, or PARTIAL) is an unresolved `impact-not-established` from V1 up, so the result is UNKNOWN, never a clean PASS (V0 is a sanity check of the changed file and does not depend on impact).
- **Summaries never show positional values**: `summarizeScript` shows the executable of each command, option names (a value only if it is a number or a boolean), plain project paths and globs, a few well-known tool and subcommand words, variable names and the operators. Every other word, URL, assignment value and `user:password` pair is replaced (`[arg]`, `[url]`, `[redacted]`), so `curl -u admin:s3cretpw https://x` is `curl -u [redacted] [url]` and `mycli login hunter2` is `mycli [arg] [arg]`. Failure excerpts redact lines that look like credentials (keywords, key and token shapes, `user:password@host`).
- **Verified forms** (`validation-classify.mjs`): a command is A1 only when its tool, subcommand, every flag and every positional argument are in that tool's table (eslint, tsc, node `--check`/`--test`, black, isort, ruff, rubocop, mypy, pyright, flake8, pylint, bandit, pytest, jest, vitest, mocha, ava, prettier, stylelint, biome, deno, bun test, golangci-lint, gofmt, read-only git queries, ...). A flag outside the table is A2 (`mutating` when it belongs to a write, cache or output family, otherwise `unclear-command`); a required check flag that is missing (`black` without `--check`, `tsc` without `--noEmit`) is A2 `mutating`; positional arguments must be plain project paths (no scheme, drive, `..`, home or secret path); build tools, `cargo`, `go`, `mvn`, `gradle` and `dotnet` write build output and are never A1; an unknown tool or an interpreter running a project script is A2. No tool is trusted by name. **Environment**: only a genuine reference (`$NAME`, `${NAME}`, `$env:NAME`, `%NAME%`) is classified as `env-expansion`; any other token (a bare `%a`, for instance) is validated like every other token. An environment assignment before a command is never ignored: a short allow-list of inert variables with plain values (`NODE_ENV`, `CI`, `FORCE_COLOR`, `NO_COLOR`, `TZ`, `LANG`, `LC_ALL`) keeps an A1 form A1; every other assignment (`NODE_OPTIONS`, `PATH`, `LD_*`, `PYTHON*`, `GIT_*`, `npm_config_*`, ...), a malformed one and `env` options are A2 `env-assignment`, never lowerable by an opt-in.
- **Shell wrappers**: for `sh -c "..."`, `bash -c`, `cmd /c`, `powershell -c` and `pwsh -Command` the quoted payload is classified like any command line (an install, download, git change, destructive or secret-reading payload is A3; network-only is A2); the wrapper itself adds `shell-construct`, which no opt-in can lower; an encoded payload is A2 and unreadable. Option families that install or write (`--install-types`, `--install-hook`, `--init`, `--fix-only`, `--unsafe-fixes`, `--snapshot-update`, `--createstub`, `--basetemp`, rubocop auto-correct) are never A1; `tsc` is read-only only with `--noEmit`.
- **Bounds** (operational): 12 actions, 8 files per syntax check, 20 targeted test files, 5 manifests, 40 scripts per manifest; each reports `{limit, total, returned, omitted, truncated}` and a limitation.

## Session continuity

Defined once in `ai/CONTINUITY.md`; this is the reference implementation (`project-intel handoff create|resume`). No second state: the only files written are `TASK_STATE.md` and `HANDOFF.md`, each by an atomic replace, and nothing is started, validated, refreshed or replayed.

```
automation/continuity-handoff.mjs   schema, identity (SHA-256 over every semantic field), render, parse, field safety, handoffRequired (pure)
automation/continuity-state.mjs     parseTaskState, ownershipOf, the one owned `## Continuity` block, withContinuity, withOwner (pure text)
automation/continuity-resume.mjs    decideResume: resume | reconcile | stop | noop | no-handoff, the drift digest, what acceptance still needs (pure)
automation/continuity-io.mjs        createHandoff, resumeHandoff, fingerprints, drift, the two atomic writes
```

- **Issue** (`handoff create --owner <name> --reason session-ending|ownership-transfer|blocked|context-too-large|user-request [--to <name>] [--next-action <text>] [--active <text>] [--caveat <text>] [--decision <text>] [--context-files <path[=why],..>] [--indexes <paths>] [--context-level 0-5]`): only the owner, and only when a trigger holds (a completed task, a task not started and a task with nothing left need none). The state is written first (`## Continuity`: task identity, `handoff-pending`, the handoff id, the receiver; the owner stays the single writer), then one `HANDOFF.md`: the template layout (the adapters' `handoff-check` still reads its `## Changed files`) plus a canonical JSON record. Its id is a SHA-256 over every semantic field (everything except the creation time); the readable text must equal the render of the record. A new handoff replaces only a valid one and names it (`previous`); an unchanged transfer is a noop; a partial write is repaired by issuing again. A handoff the tool did not issue, or one that fails its checks, is never overwritten.
- **Safety**: every field is one line, validated on the way in and again when read back. A secret-looking value, an environment assignment (or the value of a secret-named variable of the environment), a command marker (backtick, `$(`, `${`, `&&`, `||`, `|`, `;`, `<`, `>`), a structure marker, a control, zero-width or bidirectional character, an over-long field or a secret-pattern, absolute, glob or outside path is refused with a code and the field name, never redacted and never echoed; nothing is written.
- **Resume** (`handoff resume [--owner <name>]`, read-only): handoff integrity → task state and identity → ownership (the state waits on exactly this handoff, its owner issued it, the task is not completed, the asking agent is the named receiver) → the state still agrees (status, class, risk, goal, validation) → drift of the changed files, the configuration manifests (a new lockfile or manifest counts) and the referenced context (modified, deleted, reappeared, added, unverifiable) → the intelligence state now (a handoff that relies on intelligence never claims a context that is no longer current: stale, partial and unverifiable reconcile; missing and unavailable stop) → a recorded PASS is not current truth once the files it covered moved. The context plan comes from the existing router, one level at a time, starting after level 0. A repeat writes nothing.
- **Accept** (`handoff resume --accept --owner <name> --confirm <handoffId> [--acknowledge <driftDigest>]`): A2. The yes names the handoff; drift needs the digest of exactly what moved (a stop is never acknowledged away). The one write: `owner` and the `## Continuity` block (previous owner, new owner, handoff id, time, acknowledged digest). A second acceptance by the same agent is a noop; another agent is a conflict.
- **Records** are the Phase 5A format: `HANDOFF_REQUIRED` / `handoff-write` (A1), `SESSION_START` / `handoff-resume` (A1) and `SESSION_START` / `ownership-transfer` (A2); no new event or reason code.
- **Large change lists**: the changed files are carried whole (up to 400) in ordered batches of 40; the record (`erdem.handoff/2`) holds `changeSet: { total, batchSize, batches: [{ n, count, digest }] }`, each digest over its files, all inside the handoff identity. A missing, altered, duplicated, reordered or invented batch or file, a total that does not match, or a file listed twice makes the record invalid; a resume reports `changeSet: { total, batches, verified, batchesWithDrift }`. More than 400 is refused (`too-many-files`: keep a manifest file in the project and list that), a file listed twice in the state is refused (`duplicate-file`), and the handoff never holds source text.
- **Concurrent writers**: acceptance and issue take a short-lived sibling lock (`TASK_STATE.md.lock`, exclusive create; it is not an OS-level file lock; one older than 30 s is a crashed writer's and is cleared), re-read the state while holding it and decide again from what they find. Of several agents accepting the same handoff at once, exactly one is told `accepted`; the others are told `ownership-conflict` (another agent won) or `noop` (the same agent already holds it) and write nothing. A busy state is refused (`state-busy`). Residual limitation: a person editing the file by hand, or a tool that bypasses `project-intel`, is not covered: single-writer remains the protocol.
- **Refreshed intelligence is not drift**: a derived index (`--indexes`) regenerated by a refresh is not reported as moved while intelligence is current again (its bytes are the existing mechanism's deterministic output, vouched for by the engine's own status check); a deleted or unverifiable index, an index while intelligence is not current, and every other reference still are.
- **Limits**: 400 changed files (batches of 40), 16 context references, 12 items per list, 240 characters per field, 5 MB per fingerprinted file (a larger file, a link or a directory is unverifiable, never followed).
- **Release validation** (`node tools/scripts/release-validation.mjs [--json] [--only ids] [--real-claude]`): reproduces the key real-world scenarios (single agent, handoff directions, interruption, drift, validation drift, ownership race, Python impact, large handoffs, security, the flagship) in temporary projects outside the repository, through each adapter's launcher, and prints PASS, FAIL or NOT_VERIFIED per scenario; evidence the machine cannot provide (a real Codex or Antigravity agent, POSIX, a file symlink) is NOT_VERIFIED, never a pass.
