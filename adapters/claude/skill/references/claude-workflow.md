# Claude workflow

Claude Code mechanics for the Erdem workflow. Rules stay in the canonical documents; this file is how Claude applies them.

## Reading economically

- Prefer Grep and Glob over opening files; use Read with offset and limit for large files (`ai/TOKEN_EFFICIENCY.md` → Search first, Large files).
- For broad discovery ("where is X used across the project") delegate to a read-only exploration subagent so the file reads stay out of the main context; ask it for conclusions with file and line, not dumps.
- For ARCHITECTURAL work, plan first (plan mode is appropriate), then implement; do not load the architecture to start.
- Do not read secrets, generated folders or dependency folders unless the task requires it (`ai/TOKEN_EFFICIENCY.md` → Default access rules).

## Modes of `/erdem`

### design
The workflow in `SKILL.md`. Start from the matching row of `design-routing.md`; apply the rules found there (verified and approved items as rules; `proposed`, `unresolved` and `needs_reference` items as provisional, say so when you rely on one). Where a needed token has no value, do not invent one.

### review
Read-only critique of existing work against the design system. Do not edit code unless the user asks.

1. Identify the reviewed area and platform; load the matching rows of `design-routing.md`, plus `core/QUALITY_STANDARD.md`.
2. Read the target implementation (regions, not whole files).
3. Report findings, most severe first, each with: **severity**, **what**, **evidence** (`path:line`), **rule** (document and section), **rule status** (verified, approved, proposed, WCAG STANDARD, recommendation, preference), **suggested fix**.
4. Severity is this review's own scale, not a universal truth:
   - CRITICAL: a prohibited pattern, a WCAG 2.2 AA failure, or an invented token value (the FAIL column of `core/QUALITY_STANDARD.md`)
   - HIGH: clear conflict with an approved or verified rule
   - MEDIUM: conflict with a `proposed` rule or a WARNING-level criterion; or a recommendation not met
   - LOW: preference, consistency, polish
5. Separate what is a rule from what is a suggestion. Mark findings that depend on unresolved tokens as such.
6. End with what was reviewed and what was not.

### context
`erdem.mjs context`, unchanged output, nothing else.

### handoff
Update `.ai/TASK_STATE.md` and write `.ai/HANDOFF.md` using the templates, only for a meaningful transition. State what was verified and what was assumed. One next action. Pointers, not prose. Remove anything that looks like a secret before writing. If there is nothing to hand over, say so and write nothing.

## Three kinds of memory

| Scope | Lives in | Holds |
|---|---|---|
| Claude auto memory | Claude's own memory directory | personal and project learnings from corrections and preferences |
| Project state | the project: `.ai/`, its instruction files, its source | task state, handoff, decisions, architecture, conventions |
| Erdem system context | the design system | design rules and the AI protocol |

Do not save to auto memory what a repository file already records or what the design system defines; point to it instead. Repository artifacts are for cross-agent continuity (any agent can read them); auto memory is Claude-specific. Personal preferences belong in user-level Claude configuration, project rules in the project, design rules in the design system.

## Cost discipline

- The skill description is always in context; the skill body loads only when invoked; references load only when a step names them.
- After compaction Claude Code re-attaches the most recent invocation of a skill, so the skill body is kept short.
- The session-start hook adds one line. It never injects the index, task state, graph or tokens.

## Optional: path-scoped rules (not installed)

If a project later shows a repeated need, small `.claude/rules/*.md` files with a `paths:` filter could carry one-line pointers per area (web UI, mobile, 3D, backend) so the skill is nudged only when matching files are open. They are not installed or generated by this adapter: the skill plus selective references already avoids loading design context for unrelated work, and a permanent rule set would cost context on every matching session.
